# Hartevo Development Validation Ladder

状态：**Current + Target Contract**
版本：`desktop-2026-08-12-v5`

本文件定义从开发机到 E5 的唯一验证顺序。后一级不能补救前一级失败；生产环境不负责首次发现普通业务逻辑、审批、幂等、身份、归因或恢复错误。

当前工作树的实际运行结果见 [Current Worktree Evidence](./CURRENT-WORKTREE-EVIDENCE.md)。本合同中的历史数字若与其冲突，以当前证据文件和机器生成的 Release Evidence 为准。

## 1. 共同规则

- 每份结果绑定 Commit、Mission/Capability/Provider/Dataset Catalog digest、模型、Prompt/Harness、环境和时间。
- `NOT_IMPLEMENTED`、`BLOCKED_ENV`、`EXPECTED_REFUSAL`、`PARTIAL`、`FAIL` 与 `PASS` 分开统计，禁止用 `skip` 隐藏。
- 零容忍断言失败时立即停止更高层验证。
- V1/V2 的 Prompt、World delta、Rubric、Oracle、gold artifact 和 failure trace 不进入产品工作区、Target Context、Optimizer Trace 或普通 CI log。
- 外部写入必须先在 Simulator 中证明 Policy、Permission、Approval、Idempotency、Receipt、Verification 和 Recovery，再进入真实 Canary。
- 每个生产故障在关闭前必须产生最小 Replay Pack 和回归 Case。

## 3. 当前可运行命令

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features
bash scripts/check-openinterpreter-schema.sh
bash scripts/check-evidence-doc-truth.sh verify
bash scripts/check-evidence-doc-truth.sh self-test
cargo run -p hartevo-eval -- catalog validate
cargo run -p hartevo-eval -- catalog export --output target/eval/catalog-v1.json
cargo run -p hartevo-eval -- evidence baseline --commit "$(git rev-parse HEAD)" --output target/eval/release-baseline.json
cargo run -p hartevo-eval -- run --mission VS-01 --output target/eval/vs-01.json
```

`VS-01` 仍是 Bootstrap replay，不对应 VM-00～VM-11 的 E3 声明。`release-baseline.json` 必须为 `passed: false`；它用于阻止机器合同被误报为已实现产品。

### 3.1 Evidence/Docs truth gate

- `EVDOC-EV03M-01`：`VERIFIED` commit-bound manifest 只授予 manifest integrity，不授予 Release 或 Mission evidence-level authority。
- `EVDOC-B2-01` / `EVDOC-B2P-01`：Dioxus execution paint 与 exact Project/Mission private-text scope 是 `CODE_WIRED`，不是当前原生窗口 Journey 证据。
- `EVDOC-GAPS-01`：native visual、native AX、真实进程 restart/reconnect 和 Release 均保持 `NOT_PROVEN`；Release `passed=false`、decision=`NOT_EVALUATED`，Mission E-level 不提升。

`check-evidence-doc-truth.sh` 必须对固定 source/manifest Git object、B2/B2P commit scope 与上述文档投影失败关闭。它不运行也不替代 L3 原生窗口、辅助功能、真实进程恢复或 Release Evidence；这些证据未单独产出前，上述边界不得改写为 `PASS`、`PROVEN` 或更高 E-level。

## 4. L0 通过条件

1. Mission Catalog 恰好包含 `VM-00`～`VM-11`，每条具备 Goal、Mode、Cadence、Checkpoint、Artifact、Capability、Provider、Oracle、Failure Family 和 E3/E4/E5 目标。
2. 每个 Capability 双向映射 Mission；需要 Provider 的 Capability 至少由一个 Provider 暴露。
3. Mission 列出的 Provider 必须存在并与该 Mission 共享至少一项 Capability。
4. Dataset Registry 物化恰好 240 V0、120 V1 metadata、60 V2 metadata 和 180 横切 Case。
5. 每条 Mission 的 12 个 V0 基础 Case 覆盖 4 垂直×3 市场，四种资产成熟度和四种 Persona 各出现三次。
6. V1/V2 materialized metadata 中不得出现 Prompt、Checkpoint、Oracle 或 content digest。
7. Release Evidence 缺任一强制证据时不得产生 `passed: true`。

## 5. L1/L2 必测不变量

- Mission、Effect、Worker、Browser、Conversation、Creator Task 和 Settlement 状态只能沿合法边迁移。
- 金额使用 minor units + ISO currency；FX 与比例使用 Decimal 并保留来源时间。
- Approval digest 覆盖 tenant/project/mission/provider/account/resource/audience/assets/schedule/payload/money/Consent/policy/expiry。
- `uncertain` 只能 reconcile，不能自动重放。
- Webhook 验签、租户路由、去重和乱序处理为确定性逻辑。
- 人工接管或 Creator Deliverable Review 后，旧 Worker generation 不能外发或替换已审阅 digest。
- Creator Payout 只有在 KYC、资金、版本化任务合同、真实 Deliverable、文件安全/权利声明和用户接受全部成立后才能进入审批。
- 事务性 Event 与 Outbox 同时提交；重启、lease reclaim 和 dead-letter replay 都重新经过策略。

## 8. 失败关闭

- 缺 Case、结果、Catalog digest、Commit、Provider scope 或回放数据：`passed=false`。
- V1/V2 内容泄漏：废弃 Dataset revision 并轮换，不允许清理日志后继续沿用结果。
- Provider 成功但业务 readback 失败：Effect 保持未验证或失败。
- 无外部账号、KYC、签名证书或真实 cohort：报告 `BLOCKED_ENV`，不模拟 E4/E5。
- 任一跨租户、Secret、Approval、重复 Effect、Consent、金额、Handoff、Creator Payout 或 Attribution 零容忍失败：冻结发布。
